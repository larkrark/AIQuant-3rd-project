## 2. 무결성 — 봉인 ZIP 이 정본이다

```
SHA256SUMS.csv        74행 · 해시 전부 64자 (절단 없음)
봉인 ZIP 대조          일치 69 · 불일치 0 · ZIP 에 없음 5
```

**ZIP 에 없는 5건은 `05_무결성/` 자신과 ZIP 자체, `Git_인계정보.txt` 다.**
매니페스트가 자기 자신을 해싱할 수 없으므로 정상이다.

### git 사본은 해시가 재현되지 않는다 — 내용은 같다

git 사본을 SHA256SUMS 로 직접 대조하면 74건 중 68건이 불일치한다.
**전부 개행 정규화 때문이다.** 커밋 시 CRLF 가 LF 로 바뀌었고 기재 해시는
CRLF 기준이다. 개행을 정규화해 다시 대조하면 **내용 상이 0건**이다.

```
봉인 ZIP  ↔  git 사본     개행 정규화 후 69/69 동일
```

실무상 의미는 하나다. **무결성 검증은 ZIP 으로 해야 하고, git 체크아웃본으로는
성립하지 않는다.** 이 사실을 `05_무결성` 안내에 한 줄 넣어두면 수신자가 헤매지 않는다.

> 검증 과정 기록 — QA 는 1차 대조에서 5건을 "봉인 후 변경"으로 판정했다.
> 해당 파일들이 CRLF 와 LF 를 섞어 쓰고 있어 일괄 변환 검정이 걸러내지 못한 것이며,
> 정규화 후 재대조로 **오판임을 확인해 철회한다.**

## 3. 회사별 표 — 산술 검산

`QA_회사별검증대상.csv` 와 `MASTER_회사별상태표.csv` 는 **완전 동일**하다.

```
PDF = 직접대응 + PDF_ONLY      9/9 성립
XBRL = 직접대응 + XBRL_ONLY    8/9 성립
```

**효성중공업만 성립하지 않는다.**

```
효성중공업 298040   XBRL 24 ≠ 직접대응 0 + XBRL_ONLY 0
```

24건이 어느 칸에도 들어가지 않는다.

## 4. 소견 ① 효성중공업 — XBRL 이 원장 밖에 있다

`HYOSUNG_SOURCE_AVAILABILITY_LINEAGE.csv` 가 사유를 밝힌다.

```
original_collection_availability   PDF_ONLY        원 수집 시점엔 PDF 뿐
current_archive_xbrl_presence      PRESENT         현재 아카이브엔 XBRL 24건
current_archive_xbrl_zip_count     24
recorded_xbrl_reference_rows       0               원장의 XBRL 참조 기록 0
direct_pairing_record              NOT_RECORDED
retrospective_pairing              NOT_PERFORMED
technical_status                   TECHNICAL_PASS_ORIGINAL_PDF_ONLY_CONFIRMED
```

**§3 의 산술 불일치는 표의 오류가 아니라 의도된 표기다.** `XBRL_ONLY` 는
원장 안에서 XBRL 만 있는 행을 세는데, 효성의 24건은 원장 밖 아카이브라
어느 칸에도 안 들어간다.

### 그래도 소견을 남기는 이유

`원문XBRLZIP` 열이 **두 가지 의미를 섞는다.**

```
8사      원장 안에서 대응 가능한 XBRL
효성      원 수집 계보 밖의 아카이브 XBRL
```

회사별 상태표만 보면 효성도 XBRL 24 로 같아 보이고, 계보가 다르다는 사실이
그 표에서는 안 보인다. `04_기술검증증거/5D-B4C-5C` 를 열어야 알 수 있다.

**당좌비율 원장을 이 XBRL 에서 뽑으면 효성만 PIT 계보 보증이 없는 값이 된다.**
`retrospective_pairing = NOT_PERFORMED` 이므로 어느 정기보고서에 대응하는지도
확정되지 않았다.

**요청** — 회사별 상태표에 `xbrl_lineage` 열(`ORIGINAL` / `SEPARATE_ARCHIVE`)을
추가하거나, `원문XBRLZIP` 값에 계보 표시를 병기해 주십시오.
값을 쓰기 전에 소급 대응을 수행할지 여부도 결정이 필요합니다.
