# 발표 — QA·교차검증 파트 초안

담당 김민호 · 5슬라이드 · 작성 2026-07-29
담당표 근거: 72~75행(스냅샷·수기검산·독립재산출·성과비교) · 80~82행(방법론 발표 총괄)

> **이 파트의 논지**
> 성과로는 이길 수 없다. 표본 58일에 추적오차 33%면 알파를 0과 구분할 수 없기 때문이다.
> 이길 수 있는 것은 **"우리 숫자가 어떻게 나왔고 어디까지 믿을 수 있는지 안다"**는 것 하나다.
> 그래서 이 파트는 성과를 말하지 않고 검증을 말한다.

## 슬라이드 1 — 검증을 왜 따로 만들었나

### 한 줄

> 검증하는 코드가 검증받는 코드를 부르면, 그건 검증이 아니라 복사다.

### 내용

- 담당 범위: **교차검증용 백테스트 파이프라인 구축 + 수기 검산(J-5)**
- 원자료 수집에는 불참했다 — 수집자와 검증자가 같으면 교차검증이 성립하지 않는다 (담당표 19행)
- `qa/` 는 `engine/` 을 import 하지 않는다. 규칙 문서만 보고 따로 구현했다

### 네 경로로 같은 값을 만든다

| 경로 | 위치 | 무엇이 독립인가 | 무엇이 독립이 아닌가 |
|---|---|---|---|
| 파이썬 엔진 | `engine/` | 팀의 구현 | — |
| 파이썬 독립본 | `qa/independent/` | 구현이 다름 | 규칙 해석 (같은 사람) |
| 엑셀 수식 | `qa/manual_check/` | 계산 환경이 다름 | 규칙 해석 (같은 사람) |
| **사람 손** | J-5 워크시트 | **해석·계산 모두** | — |

- 위 세 경로는 **같은 오해를 공유할 수 있다.** 룰북을 잘못 읽으면 셋 다 사이좋게 틀린다
- 그것을 걸러내는 것이 네 번째, 사람이 손으로 하는 검산이다

### 말할 것

"검증 도구를 만들 때 가장 먼저 정한 것은 무엇을 보지 않을 것인가였습니다."

## 슬라이드 2 — 독립 재산출이 실제로 잡은 것

### 한 줄

> 안 맞았을 때 맞추러 가지 않고 보고했더니, 엔진 쪽이 틀린 것이었다.

### 무엇을 했나

- 룰북·데이터사전만 보고 **4~6단계를 따로 구현**했다 (상태코드 → ADTV90·시즈닝 → 구성종목·가중)
- 엔진 산출물과 항목별로 대조했다

### 처음에는 안 맞았다 — F-1

```
발견   엔진이 ADTV90 관측 종료일을 '선정일'로 잡고 있었다
문제   선정일 시점에는 아직 알 수 없는 자료가 계산에 들어갔다 (미래 정보 유입)
규칙   룰북 §5.2 · D-13 ⑧ — 관측 종료일은 '자료마감일'(선정일 이전 제5거래일)
조치   내 구현을 엔진에 맞추지 않고 F-1로 보고 → 엔진 수정 → 재대조
```

### 수정 후 결과

```
상태코드            3,303건
관측일수·시즈닝     각 36건
ADTV90              36건
P10                  4건
편입판정            36건
가중                30건
                  ─────────
불일치                 0건        10개 항목 전부 일치
```

### 이 슬라이드의 핵심

- 일치했다는 사실보다 **불일치했을 때 무엇을 했는지**가 증거다
- 결과에 맞춰 구현을 조정하지 않았다는 행동 기록이 남았다

### 말할 것

"검증의 가치는 통과율이 아니라, 안 맞았을 때 어느 쪽을 고쳤느냐에 있습니다."

## 슬라이드 3 — 검산이 성과 숫자를 바꾼 사례

### 한 줄

> 우리 지수가 기록한 −77% 폭락은 실제로 일어나지 않은 일이었다.

### 발견 경로

```
1  일별 상태 점검 중 010120(LS일렉트릭)에 거래정지 3일 + 종가 788,000 → 179,200 감지
2  분할 의심 → DART OpenDART API 로 공시 원문 확보
3  원공시   20260205800493  주식분할결정        2026-02-05
   정정공시 20260205800571  [기재정정]주식분할결정  2026-02-05
4  1주당 가액 5,000 → 1,000원 = 5:1 확정 (종가비 4.397 아님)
```

### 공시가 말해 준 세 가지

| 확인 | 내용 |
|---|---|
| **이용 가능했다** | 이사회결의일 2026-02-05 vs 3/31 회차 자료마감일 2026-03-24 → **47일 앞서 공시** |
| **경계일이 둘** | 신주 효력발생일 04-10 ≠ 신주권상장일 04-13. 가격 계열에서는 상장일이 경계 |
| **정정이 값을 갈랐다** | 원공시 주식수로 계산하면 3.33:1(오답). 액면가로 계산하면 원공시에서도 5:1 |

### 보정 결과

| 구분 | 지수 누적 | BM 대비 |
|---|---:|---:|
| as-run (분할 미반영) | +27.11% | **−14.66%p** |
| 5:1 보정 | +33.77% | **−8.00%p** |
| 차이 | +6.66%p | +6.66%p |

검산 항등식으로 확인: 종목 전 구간 수익률 차 **119.8992%p × 비중 1/18 = 6.6611%p**, 잔차 1.39e-17

### 성격 규정

- 미래 정보를 못 써서 생긴 문제가 **아니다.** 47일 전 공시를 반영하지 않은 것이다
- 따라서 보정은 **PIT 위반이 아니라 입력 오류 정정**(`INPUT_ERROR_FIX`)이다
- 드러난 구조적 결손: **저장소에 기업행사 원장이 없다.** 공시를 읽는 경로 자체가 없었다

### 말할 것

"성과가 나쁜 게 아니라 성과 숫자가 틀렸다는 걸 찾았습니다. 그리고 그건 몰라서가 아니라 안 봐서였습니다."

## 슬라이드 4 — 계산이 아니라 규칙을 검증하기

### 한 줄

> 지금의 유동성 하한은 유동성을 보지 않는다. 순위만 본다.

### 무엇을 봤나

계산이 규칙대로 됐는지만이 아니라, **그 규칙이 실제로 무엇을 하는지**를 확인했다.

### 실측 — 4개 시장 × 회차 전부 동일

| 회차·시장 | n | 최저 종목 | P10 대비 | P10 미만 |
|---|---:|---|---:|---:|
| 3/31 KR | 9 | 018260 | −53.55% | **1종목** |
| 3/31 US | 8 | ATI | −22.17% | **1종목** |
| 6/30 KR | 9 | 018260 | −12.62% | **1종목** |
| 6/30 US | 8 | KTOS | −0.55% | **1종목** |

### 우연이 아니라 구조다

```
선형보간에서 P10의 위치   h = (n − 1) × 0.10
h < 1 이면 P10은 항상 최솟값과 두 번째 값 사이에 놓인다
  →  P10 미만 종목은 언제나 정확히 1개
  →  n ≤ 10 에서 항상 성립. 2종목 이상 탈락은 n ≥ 11 이 필요
```

### 절대 유동성이 아니라 상대 순위가 결정한다

```
KTOS   3/31  329.29M (편입)  →  6/30  315.15M (탈락)
ATI    3/31  234.03M (탈락)  →  6/30  317.63M (편입)

KTOS 6/30 은 ATI 3/31 보다 34% 큰데도 탈락했다
```

부수 확인: 경계구간 `[P5, P10]` 에 들어가는 관측치가 전 회차 **0건**.
제78조 경계사례 판정은 표본 부족이 아니라 **분위수 정의상 공집합**이다.

### 이것이 만든 결과

- 팀 회의 안건이 됐다 — "P10을 절대 하한으로 볼 것인가, 상대순위 규칙으로 볼 것인가"
- 셀 최소 종목 수·개별종목 상한과 하나로 묶어 논의하기로 정리됐다
  (US 우주·방산 셀은 1종목이 16.67%를 단독 보유하며, 그 종목이 회차 간 교체됐다)

### 말할 것

"규칙이 의도대로 작동하는지 보려면 계산만 맞춰 봐서는 알 수 없습니다."

## 슬라이드 5 — 수기 검산과 한계 명시

### 한 줄

> 답을 옆에 두고 채우면 검산이 아니다. 그래서 답을 분리했다.

### J-5 수기 검산 구조

```
J5_수기검산_워크시트.xlsx      사람이 채운다 · 코드 산출값 0건
J5_코드값_봉인.xlsx            대조용 정답지 · 다 채우고 저장한 뒤에만 연다
J5_엑셀수식_교차검산.xlsx      제3의 계산 환경 · 계산 전부 엑셀 수식
audit_j5.py                    배포 전 5종 감사 게이트
```

- 초판은 빈칸 옆에 코드 답이 있었다. 확증편향으로 검산이 성립하지 않아 **파일을 분리**했다
- 누수 자동 검사를 넣었고, 실제로 1건을 잡았다 (지수 시트가 비중 답을 노출)

### 엑셀 교차검증 결과 — 12/12 일치

```
자료마감일   2026-06-23            KTOS ADTV90  315,154,781.222222
P10 하한     316,884,754.035556    편입 여부    제외
비중 합계    1.000000              최대 비중    16.666667%
지수 04-07   1,023.801567          분할 조정 전 −77.258883%
                                   분할 조정 후  13.705584%
```

엑셀 계산 엔진이 파이썬 엔진과 소수점 끝까지 일치했다.
이 과정에서 엑셀 수식 오류 9건을 잡았다(`PERCENTILE.INC` 접두어 문제).

### 반드시 함께 말할 한계

| 한계 | 내용 |
|---|---|
| 규칙 해석은 독립이 아니다 | 엑셀·독립본 모두 내가 룰북을 읽고 만든 것. 오독이면 같이 틀린다 |
| 독립 재산출은 블라인드가 아니다 | 산출물 사전 열람이 있었다. 등급은 `SPEC_ASSISTED` |
| 검산 범위 = 구현된 관문까지 | 룰북 §9는 재무조건을 요구하나 미구현. 시즈닝·유동성 2개 관문만 적용 |
| **검산 통과 ≠ 성과 신뢰** | 검산은 계산이 규칙대로 됐는지만 말한다 |

### 성과에 대해 말할 수 있는 것

```
표본 58일 · 추적오차 32.57% · 연율 알파 −25.25%
알파 표준오차 ±67.90%  →  t = −0.372
95% 신뢰구간 대략 −161% ~ +111%
```

> **알파가 0과 구분되지 않는다. "성과가 낮다"도 "성과가 좋다"도 말할 수 없다.**
> 그리고 구성종목은 규칙이 유니버스에서 뽑은 것이 아니라 시험용 Seed 18종목이다.
> 우리는 아직 성과를 측정한 적이 없다. 지금 있는 것은 규칙과 자료구조가 작동하는지 확인한 결과다.

### 말할 것

"검산이 맞았으니 성과도 믿을 만하다 — 이 말은 하지 않겠습니다. 두 가지는 다른 이야기입니다."

## 발표 시 주의

**하지 말아야 할 말**

- "검증을 통과했으니 결과가 정확하다" — 검산은 계산 정합성만 말한다
- "제대로 된 유니버스로 하면 더 좋았을 것이다" — 근거 없고, 성과기반 변경으로 읽힌다
- "완전 블라인드 검증" — 독립 재산출은 `SPEC_ASSISTED`다

**숫자 인용 규칙**

- as-run과 보정본을 병기한다: `−14.66%p / 5:1 보정 −8.00%p(QA 참고본, 엔진 정식 재산출 전)`
- 6.66%p(누적 %p 차)와 5.24%(상대 수익률 차)를 섞지 않는다
